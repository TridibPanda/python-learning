SECTION 0 — OCI ARCHITECTURE FUNDAMENTALS
================================================================================

CORE HIERARCHY (top to bottom):
  Realm → Region → Availability Domain (AD) → Fault Domain (FD)

DEFINITIONS:
  Realm:  Group of regions sharing same Oracle infrastructure.
          OC1 = Commercial (public cloud)
          OC2 = Government (US Federal)
  Region: Geographic area with 1 or more ADs.
          Tenancy subscribes to regions individually.
  AD:     Isolated data center within a region.
          1–3 ADs per region (exam: most have 3, some have 1).
          ADs in same region connected via low-latency Oracle network.
          Failure in one AD does NOT affect other ADs.
  FD:     Logical grouping of hardware WITHIN an AD.
          Protects against hardware/power failure within same AD.
          Always exactly 3 FDs per AD.
          FDs do NOT share physical hardware with each other.

RESOURCE SCOPE:
  GLOBAL (not region-specific):   IAM (compartments, policies, users, groups, tags)
  REGIONAL:                       VCN, Subnets (regional), Object Storage, LB, Reserved IPs
  AD-SPECIFIC:                    Compute instances, Block Volumes, File Storage Mount Targets
  TENANCY ROOT:                   Root compartment = top-level; exists always; cannot delete

KEY NUMBERS TO MEMORISE:
  ADs per region:           1–3
  FDs per AD:               3 (always exactly 3)
  Max compartment depth:    6 levels deep
  Max VCNs per DRG:         300

SECTION 1 — IAM (Identity and Access Management)
================================================================================

GOLDEN RULE: OCI defaults to DENY everything. Policies only ALLOW. No explicit deny.

POLICY SYNTAX:
  Allow <subject> to <verb> <resource-type> in <location> [where <condition>]
  Examples:
    Allow group Admins to manage all-resources in tenancy
    Allow group DevTeam to use instances in compartment Prod
    Allow dynamic-group MyGroup to read object-family in tenancy

VERB HIERARCHY (least → most powerful):
  inspect → read → use → manage
  inspect:  List resources only (no sensitive data shown)
  read:     List + get resource details
  use:      Read + use resource (no create/delete)
  manage:   Full control — create, read, update, delete
  TRAP: manage includes all lower verbs. inspect is LEAST powerful.

SUBJECT TYPES:
  group, dynamic-group, any-group, any-user, service, specific OCID
  ALWAYS prefix domain name: domainName/GroupName
  Omitting domain prefix = default domain implied
  TRAP: any-group  = all users + instance principals + resource principals (RECOMMENDED)
  TRAP: any-user   = same as any-group PLUS service principals (NOT recommended by Oracle)
  TRAP: Use any-group over any-user — Oracle explicitly recommends any-group instead

IDENTITY RESOURCE TYPE TRAP:
  Identity resources have NO aggregate resource type.
  Must list individually: users, groups, policies, dynamic-groups, identity-providers, etc.
  (You CANNOT write "manage identity-family" — there is no aggregate for IAM)

IDENTITY DOMAIN TYPES:
  +---------------------------+--------------------------------------------------+
  | Type                      | Key Facts                                        |
  +---------------------------+--------------------------------------------------+
  | Free                      | Default type; 2,000 users; basic OCI access      |
  | Oracle Apps               | Auto-assigned with SaaS purchase; CANNOT create  |
  | Oracle Apps Premium       | Hybrid IAM; max 10 non-Oracle apps              |
  | Premium                   | ALL features; high limits; full enterprise IAM   |
  |                           | Includes everything in Free + Oracle Apps +      |
  |                           | Oracle Apps Premium + External User capabilities |
  | External User             | Consumers/social login; non-employees            |
  +---------------------------+--------------------------------------------------+

DEFAULT DOMAIN:
  - Automatically created in ROOT compartment when tenancy provisioned
  - CANNOT delete, deactivate, or hide the default domain
  - Auto-replicates to ALL subscribed regions (AUTOMATIC — no action needed)

EXTRA DOMAINS:
  - NOT auto-replicated
  - Must manually enable replication per region

DEFAULT GROUPS (cannot delete either one):
  Domain Administrators:  Must always have at least 1 user
  All Domain Users:       Hidden; auto-assigned to every user; cannot delete

COMPARTMENTS:
  - Global (not region-specific)
  - Max 6 levels deep
  - 1 resource lives in exactly 1 compartment (cannot be in two)
  - Resources CAN interact cross-compartment
  - Root compartment = tenancy level

POLICY INHERITANCE:
  - Policy attached to a compartment = applies to that compartment + ALL child compartments
  - Policy attachment location = who can modify that policy
  - TRAP: attach to tenancy = anyone with tenancy admin can change it

QUOTA POLICY:
  - Actions: set / unset / zero
  - * wildcard = applies to ALL resource types in a service family
  - Different from IAM policies (quotas limit capacity, not access)

DYNAMIC GROUPS:
  - Match resources (usually compute instances) by:
      instance OCID
      compartment OCID
      tag value (defined tag)
  - Used to give instances permissions without storing credentials

CONDITIONAL POLICIES (where clause):
  any{} = OR logic (at least one condition must match)
  all{} = AND logic (all conditions must match)
  request.*  = attributes of the incoming request
  target.*   = attributes of the target resource
  request.permission     = permission name in ALL CAPS (e.g., VOLUME_INSPECT)
  request.operation      = exact API operation name

NETWORK SOURCES:
  - Restrict a policy so it only applies from specific network locations
  - Specify on-prem CIDRs or VCN CIDRs in a named Network Source
  - Use in policy: where request.networkSource.name = 'CorpNetwork'

TAG-BASED ACCESS:
  - Use defined tag conditions in where clause
  - Allows policies to span compartments based on tags (not just location)

SECTION 2 — NETWORKING: VIRTUAL CLOUD NETWORK (VCN)
================================================================================

VCN BASICS:
  - Spans ALL ADs in a region (VCN is a regional resource)
  - CIDR range: /16 (largest — 65,536 IPs) to /30 (smallest — 4 IPs)
  - Can assign multiple CIDR blocks to one VCN (max 16 IPv4 CIDRs per VCN; max 16 IPv6 prefixes per VCN)
  - Local VCN traffic (within VCN): no route rule needed — automatic

SUBNETS:
  Regional subnet:   Spans all ADs in the region (recommended, modern default)
  AD-specific subnet: Tied to one specific AD only
  Public subnet:     Resources CAN have public IPs; has route to Internet Gateway
  Private subnet:    Resources have private IPs only; no direct internet access; use NAT for outbound

SECURITY LIST vs NSG:
  +---------------------+-----------------------------+-----------------------------+
  | Feature             | Security List               | NSG                         |
  +---------------------+-----------------------------+-----------------------------+
  | Scope               | Subnet level                | Individual VNIC/resource    |
  | Applies to          | ALL VNICs in the subnet     | Only VNICs added to NSG     |
  | Max per subnet/VNIC | 5 security lists per subnet | 5 NSGs per VNIC             |
  | Source/Dest rules   | CIDR only                   | CIDR OR another NSG         |
  | Stateful            | Yes (default)               | Yes (default)               |
  | Stateless rules     | Configurable                | Configurable                |
  +---------------------+-----------------------------+-----------------------------+
  TRAP: NSG can reference another NSG as source/dest — Security List CANNOT.
  TRAP: Both are stateful by default.

  Standard port numbers:

Port	Protocol	   Use for
22	   SSH	      Secure remote login to Linux/Unix instances
80	   HTTP	      Web traffic (unencrypted)
443	   HTTPS	      Web traffic (encrypted/TLS)
3389	   RDP	      Remote Desktop — Windows instances

GATEWAY COMPARISON TABLE:
  +--------------------+-------------------+--------------------------------------------+
  | Gateway            | Direction         | Use Case                                   |
  +--------------------+-------------------+--------------------------------------------+
  | Internet Gateway   | Bidirectional     | Public subnet <-> Internet                 |
  | NAT Gateway        | Outbound ONLY     | Private subnet -> Internet (no inbound)    |
  | Service Gateway    | Private only      | OCI services without internet (Object Str) |
  | Local Peering (LPG)| Bidirectional     | Same-region VCN-to-VCN peering             |
  | DRG                | Bidirectional     | On-prem / cross-region / cross-VCN         |
  +--------------------+-------------------+--------------------------------------------+
  TRAP: NAT Gateway = OUTBOUND only. No inbound traffic allowed.
  TRAP: Service Gateway = private traffic only. No internet routing.

ROUTE TABLES:
  - Attached to subnets (defines where traffic goes when leaving the subnet)
  - Rules format: destination CIDR -> target gateway
  - Local VCN CIDR: automatic (no explicit route rule needed)
  - Public subnet internet route: 0.0.0.0/0 -> Internet Gateway
  - Private subnet internet route: 0.0.0.0/0 -> NAT Gateway

SECTION 3 — NETWORKING: IP MANAGEMENT
================================================================================

EPHEMERAL vs RESERVED PUBLIC IP:
  +---------------------+----------------------------+----------------------------+
  | Feature             | Ephemeral IP               | Reserved IP                |
  +---------------------+----------------------------+----------------------------+
  | Assignment          | Auto-assigned at creation  | Created independently      |
  | On termination      | RELEASED / LOST            | PERSISTS (survives)        |
  | Moveable            | NO (tied to VNIC)          | YES (move between VNICs)   |
  | During stop/start   | Retained                   | Retained                   |
  | Per VNIC            | 1 (primary VNIC)           | 1 per VNIC                 |
  +---------------------+----------------------------+----------------------------+
  TRAP: Ephemeral IP is LOST when instance terminates. Reserved IP survives termination.

BYOIP (Bring Your Own IP):
  - Bring your own public IP prefix to OCI
  - Minimum prefix size: /24 for IPv4
  - Create Public IP Pools from BYOIP prefix for controlled IP assignment
  - Useful for organisations that need specific IPs whitelisted externally

SECTION 4 — NETWORKING: CONNECTIVITY
================================================================================

--- BGP ---
  FastConnect ALWAYS uses BGP (mandatory — no alternative routing protocol).
  Site-to-Site VPN: supports static routing, BGP, or policy-based routing.
  BGP = Border Gateway Protocol (dynamic routing; exchanges routes automatically).

--- DRG (Dynamic Routing Gateway) ---
  What it is: Virtual router that connects VCNs to on-prem, other regions, other VCNs.

  ATTACHMENT TYPES (6):
    VCN attachment
    RPC (Remote Peering Connection)
    IPsec VPN tunnel
    Virtual Circuit (FastConnect)
    Loopback attachment
    Cross-tenancy VCN attachment

  KEY NUMBER:
    Up to 300 VCNs per DRG

  DEFAULT ROUTE TABLES (2 auto-created when DRG is provisioned):
    Table 1 — for VCN attachments:          learns routes from ALL attachment types
    Table 2 — for RPC/VC/IPsec attachments: learns VCN routes ONLY

  ROUTE CONFLICT PRIORITY (highest wins):
    Static > VCN > Virtual Circuit (FastConnect) > IPsec (VPN) > RPC

  ECMP (Equal Cost Multi-Path Routing):
    OFF by default (must explicitly enable)
    Enabled per DRG route table
    Distributes traffic across multiple equal-cost circuits/tunnels via BGP
    Use when you have multiple FastConnect circuits or multiple VPN tunnels

  IMPORTANT RULE:
    IPsec and Virtual Circuit routes are NEVER exported to other IPsec or VC attachments.
    (On-prem routes stay between on-prem attachments and VCNs only)

--- SITE-TO-SITE VPN ---
  - Encrypted IPsec connection over public internet (not private)
  - Connects on-prem network to OCI VCN

  IPSEC MODES:
    Tunnel Mode:    Encrypts ENTIRE packet (header + payload) — Oracle supports THIS
    Transport Mode: Encrypts payload only — Oracle does NOT support this
    TRAP: Always choose Tunnel Mode for Oracle VPN

  TUNNEL FACTS:
    Each VPN connection = 2 redundant tunnels (both active for HA)
    Each tunnel has its own: public IP address + pre-shared key
    Up to 8 IPsec connections per CPE (Customer Premises Equipment) public IP

  ROUTING OPTIONS PER TUNNEL:
    - Static routing (manually define routes)
    - BGP routing (dynamic, learns routes automatically)
    - Policy-based routing (define traffic selectors)
    Best practice: use same routing type on both tunnels

  IKE (Internet Key Exchange):
    Supports IKE v1 and IKE v2
    CPE behind NAT: change IKE identifier to CPE's private IP address

--- FASTCONNECT ---
  - Dedicated PRIVATE physical connection to OCI
  - NEVER traverses public internet
  - NO egress data transfer charges (unlike VPN)
  - ALWAYS uses BGP (mandatory)

  FastConnect = data transfer fully FREE (no ingress, no egress charges)
VPN = ingress FREE, egress CHARGEABLE
FastConnect = you pay for the port/circuit (dedicated line fee)
VPN = you pay for egress data (internet transfer fee)

  3 FASTCONNECT MODELS:
  +---------------------------+---------------------+------------------------------------+
  | Model                     | LOA Required?       | Key Notes                          |
  +---------------------------+---------------------+------------------------------------+
  | Oracle Partner            | NO                  | Pre-established link at partner    |
  |                           |                     | Cheapest and most flexible         |
  |                           |                     | Layer 2 or Layer 3 partner         |
  | Third-Party Provider      | YES -> to carrier   | Carrier provisions cross-connect   |
  | Co-location               | YES -> DC technician| Customer cage at FC location       |
  +---------------------------+---------------------+------------------------------------+
  LOA = Letter of Authorization
  TRAP: Oracle Partner does NOT need LOA. The other two DO.

  VIRTUAL CIRCUIT TYPES:
    Private Virtual Circuit: connects to VCN; DRG required at OCI end
    Public Virtual Circuit:  connects to OCI public services; NO DRG needed

  ORACLE PARTNER TYPES:
    Layer 2 partner: BGP terminates directly at Oracle; each VC needs different physical router
    Layer 3 partner: BGP terminates at partner edge router; single VC is auto-redundant

  FASTCONNECT REDUNDANCY:
    Minimum 2 physical routers per FastConnect location
    Third-party/colocation: use 2 VCs on 2 physical connections to 2 different edge devices
    VPN as FastConnect backup: FastConnect takes priority when same routes advertised on both

--- VCN PEERING ---
  +--------------------+----------------------------+-----------------------------+
  | Feature            | Local Peering              | Remote Peering              |
  +--------------------+----------------------------+-----------------------------+
  | VCN location       | Same region                | Different regions           |
  | Gateway used       | LPG x2 (OR DRG v2)         | DRG x2 + RPC x2             |
  | Cross-tenancy      | Yes (DRG v2)               | Yes (DRG v2 only)           |
  | Traffic path       | Oracle backbone            | Oracle backbone             |
  +--------------------+----------------------------+-----------------------------+
  TRAP: LPG = Local Peering Gateway. RPC = Remote Peering Connection on DRG.

--- TRANSIT ROUTING ---
  Architecture: Hub-and-spoke topology
  - Hub VCN connects to on-prem via single VPN or FastConnect connection
  - Spoke VCNs connect to hub VCN via LPGs (Local Peering Gateways)
  - Spoke VCNs reach on-prem through the hub (no direct on-prem connection needed)

  REQUIREMENTS:
    All VCNs MUST be in SAME REGION
    Different tenancies: ALLOWED
    6 route tables needed total (hub has extra route tables on LPGs and DRG)
    LPG route table target: must be DRG or a private IP (NOT IGW, NAT, or SGW)

SECTION 5 — NETWORKING: LOAD BALANCER
================================================================================

PUBLIC vs PRIVATE LOAD BALANCER:
  +------------------------+--------------------------+---------------------------+
  | Feature                | Public LB                | Private LB                |
  +------------------------+--------------------------+---------------------------+
  | Subnet type            | Public subnet            | Private subnet            |
  | IP address type        | Public IP                | Private IP only           |
  | Internet accessible    | YES                      | NO (VCN-internal only)    |
  | Subnets required       | 1 regional OR            | 1 subnet only             |
  |                        | 2 AD-specific subnets    |                           |
  | IPs consumed           | 2 private + 1 floating   | 3 private IPs             |
  |                        | public IP                | (primary + standby +      |
  |                        |                          | floating)                 |
  +------------------------+--------------------------+---------------------------+

LB vs NETWORK LOAD BALANCER (NLB):
  +---------------------+---------------------------+-----------------------------+
  | Feature             | Load Balancer (LB)        | Network Load Balancer (NLB) |
  +---------------------+---------------------------+-----------------------------+
  | OSI Layer           | Layer 4 + Layer 7         | Layer 3 + Layer 4           |
  | Source IP preserved | NO (replaced by LB IP)    | YES (original source IP)    |
  | Bandwidth           | 10–8,000 Mbps (configured)| Elastic (auto-scales)       |
  | Latency             | Standard                  | Ultra-low                   |
  | LB Policies         | Round Robin               | 5-tuple hash                |
  |                     | Least Connection          | 3-tuple hash                |
  |                     | IP Hash                   | 2-tuple hash                |
  +---------------------+---------------------------+-----------------------------+
  TRAP: NLB PRESERVES source IP. Regular LB REPLACES it with LB IP.
  TRAP: NLB bandwidth = elastic/automatic. LB = must configure min and max.
  Load Balancer	Protocols
NLB (Network LB)	TCP, UDP, ICMP — Layer 3/4 only
Regular LB	HTTP, HTTPS + TCP — Layer 4 + Layer 7
WAA = Layer 7 LB only = HTTP and HTTPS only
Protocol	OSI Layer	  Regular LB	  NLB
TCP	       Layer 4	     YES	      YES
UDP	       Layer 4	      NO	      YES
HTTP/HTTPS Layer 7	     YES	      NO
ICMP	     Layer 3	      NO	      YES

LB SHAPE:
  - Flexible shape ONLY (dynamic shape was discontinued)
  - Minimum bandwidth = readiness (guaranteed minimum baseline)
  - Maximum bandwidth = cost control (ceiling — won't exceed this)

LB POLICIES:
  Round Robin:      Default; distributes requests sequentially.
                    Best for backends with similar capacity and similar request load.
  Least Connection: Sends to backend with fewest active connections.
                    Best for variable request load (some requests take much longer).
  IP Hash:          Same client IP always goes to same backend.
                    Client-IP-based sticky routing (not cookie-based).

POLICY BEHAVIOR BY PROTOCOL:
  TCP connections:       Policy applies to FIRST packet only; subsequent follow same connection
  HTTP non-sticky:       Policy evaluated on EVERY new request
  HTTP with sticky:      Cookie determines routing (overrides the policy choice)

HEALTH CHECK DEFAULTS:
  Interval (between checks):  10 seconds
  Timeout (per check):        3 seconds
  Retries:                    3
  TRAP: Retries = 3 for BOTH unhealthy threshold AND for recovery (same number both ways).

SSL MODES:
  +---------------------+------------------------------------------------------------+
  | Mode                | What Happens                                               |
  +---------------------+------------------------------------------------------------+
  | SSL Termination     | LB decrypts TLS; backend receives plain HTTP               |
  | Point-to-Point      | LB decrypts then re-encrypts; backend receives TLS         |
  | SSL Tunneling       | LB passes encrypted traffic as-is; NO decryption at LB    |
  +---------------------+------------------------------------------------------------+

SESSION PERSISTENCE:
  Application Cookie:  Client sends existing app cookie; LB identifies backend by cookie
  LB Cookie:           LB creates and manages its own session cookie

WAA — WEB APPLICATION ACCELERATION (Layer 7 LB ONLY):

  CACHING RULES:
    ONLY caches:       HTTP 200 responses + GET or HEAD methods
    Does NOT cache:    Responses with Set-Cookie header
    Does NOT cache:    Responses with Cache-Control: no-cache header
    Does NOT cache:    Responses with Cache-Control: private header
    Does NOT cache:    Dynamic pages / personalised content
    Max object size:   100 MB per cached object
    Eviction policy:   LFU (Least Frequently Used)
    Default TTL:       10 minutes
    Cache purge:       IRREVERSIBLE — cannot undo once purged

  COMPRESSION RULES:
    Method:            gzip ONLY
    TRAP: Cannot enable compression without ALSO enabling caching

SECTION 6 — DNS MANAGEMENT
================================================================================

DNS QUERY FLOW:
  Browser -> Recursive DNS server -> Root Servers (.)
  -> TLD servers (.com) -> Authoritative DNS -> IP address returned -> Browser loads page

OCI DNS BENEFITS:
  - Lowest latency (queries served via anycast from OCI global regions)
  - Built-in DDoS(Distributed Denial of Service) protection (resilient against outages)
  - Industry-leading propagation speed
  - Import zones via standard BIND zone data format

ZONE TYPES:
  Public Zone:   Holds DNS records for public internet access
  Private Zone:  Resolves DNS names for private addresses within VCN

PUBLIC DNS ZONE — 3 STEPS:
  Step 1: Create public DNS zone in OCI
          (auto-creates NS record and SOA(Start of Authority) record)
  Step 2: Delegate the zone
          Copy OCI nameserver (NS) records -> paste into domain registrar DNS panel
          (This makes OCI authoritative for your domain)
  Step 3: Add DNS records to zone
          (A, AAAA, CNAME, MX, TXT, etc.)

DNS RECORD TYPES (know these for exam):
  A:    Maps hostname -> IPv4 address
  AAAA: Maps hostname -> IPv6 address
  CNAME:Alias pointing to another hostname
  MX:   Mail server for the domain
  NS:   Nameserver record (auto-created with zone)
  SOA:  Start of Authority (auto-created with zone)
  TXT:  Text record (verification, SPF, DKIM)

PRIVATE DNS (3 VCN OPTIONS):
  Option 1 — Internet + VCN Resolver (default):
    Resolves public internet hostnames AND instances within same VCN
  Option 2 — Custom Resolver:
    Use your own DNS server (on internet, in VCN, or on-prem)
  Option 3 — Private DNS Zones:
    Internal domain names only; not exposed to internet

PRIVATE VIEWS:
  - Collection of private DNS zones (logical grouping)
  - ONE zone can only belong to ONE view (cannot be in multiple views)
  - ONE view can be used by MULTIPLE resolvers (shareable across VCNs)
  - VCN resolver always has a default view; can attach additional custom views

HTTP REDIRECTS:
  301 = Moved Permanently (permanent; tell search engines and browsers)
  302 = Temporary redirect
  MUST create CNAME record in DNS zone for redirect to work

TRAFFIC MANAGEMENT STEERING POLICIES (5 types):
  +---------------------------+----------------------------------------------------+
  | Policy Type               | What It Does                                       |
  +---------------------------+----------------------------------------------------+
  | Failover                  | Primary -> Secondary when primary is unhealthy     |
  | Load Balancer             | Weighted distribution (50/50, 10/90, custom ratio) |
  | Geolocation Steering      | Route based on user's geographic location          |
  | ASN Steering              | Route based on Autonomous System Number            |
  | IP Prefix Steering        | Route based on originating IP prefix               |
  +---------------------------+----------------------------------------------------+
  Use cases:
    Failover:      High availability, DR
    Load Balancer: Cloud migration (start 10% new, increase gradually)
    Geolocation:   Worldwide traffic distribution
    ASN:           Mobile operator routing, zero-rating services
    IP Prefix:     Canary testing (internal vs external users)

SECTION 8 — COMPUTE
================================================================================

SHAPE TYPES:
  +----------------------+-------------------------------------------------------+
  | Shape Type           | Key Facts                                             |
  +----------------------+-------------------------------------------------------+
  | Fixed Shape          | Cannot customise OCPUs/memory (fixed specs)           |
  |                      | Supports Bare Metal (BM) + VM                         |
  | Flexible Shape       | Customise OCPUs and memory within defined limits      |
  |                      | VM ONLY (no Bare Metal flexible shapes)               |
  |                      | Max: 64 GB memory per OCPU                            |
  |                      | Network bandwidth scales automatically with OCPUs     |
  +----------------------+-------------------------------------------------------+
  TRAP: Flexible shapes are VM ONLY. Cannot use flexible on Bare Metal.

BARE METAL (BM) vs VM:
  Bare Metal: Dedicated physical server; no hypervisor overhead.
              Use for: BYOL licensing, high-performance workloads, custom hypervisor.
  VM:         Virtualised; runs on BM via Oracle hypervisor; multi-tenant; flexible.

PREEMPTIBLE INSTANCES:
  Cost:                 50% cheaper than equivalent on-demand instance
  Termination:          Oracle can terminate at any time (if capacity needed)
  Notice:               30 seconds warning before termination
  Cannot:               Change shape or convert to on-demand
  Support:              VM only (NO Bare Metal preemptible)

BURSTABLE INSTANCES:
  Purpose:              Baseline CPU with ability to burst higher for spikes
  Baseline options:     12.5% or 50% of each OCPU
  Billing:              Billed at BASELINE OCPU rate (even when bursting)
  CPU bursts:           YES (when physical host has spare capacity)
  Memory bursts:        NO — memory NEVER bursts
  Burst guarantee:      NONE — burst only if host has spare capacity
  Burst eligibility:    Average CPU must be below baseline over last 24 hours
  Supported shapes ONLY: VM.Standard3.Flex, VM.Standard.E3.Flex, VM.Standard.E4.Flex, VM.Standard.E5.Flex

DEDICATED VM HOST (DVH):
  What it is:   Entire BM server dedicated to ONE customer's VMs (single-tenant)
  Billing:      Billed for DVH as soon as created; NOT billed for VMs on it
  Use cases:    Compliance/regulatory isolation; host-based BYOL licensing
  NOT supported on DVH (exam trap — these 6 things cannot run on DVH):
    1. Autoscaling
    2. Capacity reservations
    3. Instance configurations
    4. Instance pools
    5. Burstable instances
    6. Remote migration

VERTICAL SCALING:
  What it is:   Change shape of a VM (scale up/down) without rebuilding
  REBOOT:       Instance IS REBOOTED if running when shape is changed
  Unchanged:    IP addresses, VNIC attachments, block volume attachments all stay

INSTANCE CONFIGURATION:

SECTION 11 ADDENDUM — FILE STORAGE: ADVANCED TOPICS
================================================================================

--- FILE STORAGE: 3 CORE CONSTRUCTS ---
  File System:    Where files actually live (the storage layer)
  Export:         NFS control layer — controls client access to file system;
                  links a file system to a mount target
  Mount Target:   NFS endpoint (IP or DNS name) in a subnet;
                  highly available; one mount target can serve MULTIPLE file systems

  RELATIONSHIP:
    NFS Client → Mount Target → Export → File System
    One mount target → many exports → many file systems (up to 100)
    File system must have at least 1 export before instances can mount it

--- NFS EXPORT OPTIONS ---
  4 parameters per export option entry:
  1. Source:  IP address or CIDR block of NFS client
  2. Ports:   Privileged (root only) or Any
  3. Access:  Read-Only or Read-Write
  4. Squash:  All (remap all UIDs/GIDs to anon) /
              Root (remap only root) /
              None (no remapping)

  Max export options: 100 per export

  FIRST-MATCH RULE (CRITICAL EXAM TRAP):
    The FIRST export option entry that matches the client IP is applied.
    All remaining entries are IGNORED after first match.
    MORE SPECIFIC rules (single IP) must come BEFORE more general rules (CIDR).
    TRAP: 10.0.0.8 Read-Write listed AFTER 10.0.0.0/16 Read-Only →
          client 10.0.0.8 gets Read-Only (matched first by the /16 rule)

  DENY ACCESS COMPLETELY:
    Ensure client IP/CIDR is NOT in any export option entry for that file system.
    No match = no access.

--- FILE STORAGE: 3 PATH TYPES ---
  +-------------------+---------------------------+-------------------------------------+
  | Path Type         | Where it lives            | Purpose / Example                   |
  +-------------------+---------------------------+-------------------------------------+
  | Export Path       | Mount Target level        | Identifies FS within mount target   |
  |                   |                           | /FileSystem-export1                 |
  |                   |                           | CANNOT edit after export created    |
  | Mount Point Path  | Client instance           | Local directory where FS is mounted |
  |                   |                           | /mnt/myfilesystem                   |
  | File System Path  | Inside the file system    | Directories/files in the FS         |
  |                   |                           | Snapshots: /.snapshot/snap-name     |
  +-------------------+---------------------------+-------------------------------------+

--- FILE STORAGE SNAPSHOTS ---
  Consistent, point-in-time view of a file system
  Access path: <mount-point>/.snapshot/<snapshot-name>
  Initial storage: ZERO (references original data, no copy at creation)
  Storage grows: Only for changed/new blocks since last snapshot
  File recovery: Browse .snapshot directory and copy files back

--- FILE STORAGE CLONING ---
  What it is:   Creates a new file system from an existing file system or snapshot
  Independent:  After clone, source and clone are completely independent
  Initial cost: Zero (clone shares storage with source initially, COW model)
  Storage grows: Only as clone diverges from source

--- FILE STORAGE REPLICATION ---
  Ongoing async replication of file system to another availability domain/region
  Used for: Disaster recovery, data migration
  Base copy: Initial full sync
  Delta cycles: Subsequent syncs of only changed data

--- FILE STORAGE: 4 SECURITY LAYERS ---
  Layer 1: IAM policies (controls who can manage File Storage resources)
  Layer 2: Network security (Security Lists / NSGs — controls TCP/UDP access)
  Layer 3: NFS Export Options (controls per-client access at export level)
  Layer 4: Unix security (POSIX file permissions on files/directories)
  TRAP: All 4 layers work together — a client must pass ALL 4 to access a file

WHAT IS VAULT:
  OCI Vault = OCI's Key Management Service (KMS)
  Used to: create, store, manage cryptographic keys and secrets
  Keys protect data at rest in Object Storage, Block Volumes, File Storage, DB, etc.
  Vault itself is a logical container for keys and secrets

KEY TYPES:
  +--------------------+---------------------------------------------------+
  | Type               | Details                                           |
  +--------------------+---------------------------------------------------+
  | Software Key       | Stored in software; cheaper; lower security       |
  | HSM Key (Managed)  | Stored in Hardware Security Module (physical HW)  |
  |                    | Tamper-resistant; FIPS 140-2 Level 3 certified    |
  |                    | Higher security; cannot be exported               |
  +--------------------+---------------------------------------------------+
  TRAP: HSM keys CANNOT be exported — they never leave the HSM.

KEY ALGORITHMS:
  AES:   Symmetric; used for data encryption (AES-128, AES-192, AES-256)
  RSA:   Asymmetric; used for digital signatures and data encryption
  ECDSA: Asymmetric; used for digital signatures

ENCRYPTION MODEL (2 layers):
  Master Encryption Key (MEK):  Stored in Vault; never touches your data directly
  Data Encryption Key (DEK):    Encrypts the actual data; wrapped (encrypted) by MEK
  This is called ENVELOPE ENCRYPTION.
  TRAP: Data is encrypted by DEK. DEK is encrypted by MEK. MEK lives in Vault.

KEY ROTATION:
  Rotating a key creates a new KEY VERSION
  Old versions kept so existing data can still be decrypted
  New data encrypted with new key version
  Oracle-managed keys rotate automatically
  Customer-managed keys: you control rotation schedule

BYOK (Bring Your Own Key):
  Import your own key material into OCI Vault
  Use existing enterprise keys from on-prem HSM

VAULT TYPES:
  Virtual Private Vault: dedicated HSM partition; isolated; higher cost
  Default Vault:         shared; lower cost; good for most use cases

SECRETS:
  Store sensitive config data (passwords, tokens, API keys) in Vault
  Secrets have versions; can rotate secret values
  Applications retrieve secrets at runtime (no hard-coding)

CROSS-AD REPLICATION RESTRICTION (exam trap repeated):
  Block Volume cross-AD and cross-region replication:
  NOT supported when volume encrypted with customer-managed Vault keys

    OK_TO_FIRING: Alarm just crossed threshold → now FIRING
    FIRING_TO_OK: Alarm resolved normally → back to OK
    REPEAT:       Alarm still FIRING (sent at configured repeat interval)
    RESET:        Alarm returned to OK after internal reset (metric stream was absent)
    TRAP: RESET is a MESSAGE TYPE, NOT an alarm state. State is OK when RESET fires.
    TRAP: Internal reset = 10 min period; alarm stops tracking an absent metric stream.

  ALARM CONFIGURATION:
    Query:        MQL metric query (e.g. CpuUtilization > 80)
    Trigger delay: How long metric must exceed threshold before alarm fires
    Notifications: ONS topic to notify when alarm fires or resolves
    Suppression:  Can suppress alarm during maintenance windows

  IMPORTANT:
    Alarms use ONS Topics to deliver notifications.
    One alarm can notify multiple subscribers via one topic.

--- ONS — OCI NOTIFICATIONS SERVICE ---
  What it is:   Publish-Subscribe (Pub/Sub) messaging service
  Topic:        Named channel for messages (alarms, events publish TO a topic)
  Subscription: Endpoint subscribed to a topic to receive messages

  SUBSCRIPTION PROTOCOLS (what receives the message):
    Email
    HTTPS (webhook / REST endpoint)
    PagerDuty
    Slack
    SMS (limited regions)
    OCI Functions (serverless function triggered)
    OCI Queue

  FLOW:
    Source (Alarm / Events Rule) → publishes to ONS Topic
    ONS Topic → delivers to all subscriptions
    Subscriptions → notify Email / Slack / HTTPS / Function / etc.

  TRAP: ONS is the DELIVERY mechanism. Alarms and Events are the SOURCES.

--- OCI EVENTS SERVICE ---
  What it is:   Automatically captures state changes in OCI resources
  Trigger:      When an OCI resource changes state (created, terminated, updated, etc.)
  Actions:      Send to ONS Topic / Invoke Function / Stream to OCI Streaming

  EVENT RULE:
    Condition:    Filter by event type, resource type, compartment, tags
    Action:       What to do when condition matches (notify, trigger function, etc.)

  EXAMPLES:
    Bucket created → notify security team via ONS
    Instance terminated → trigger cleanup function
    Volume backup completed → send email

  TRAP: Events = resource state changes. Alarms = metric threshold breaches.
        Different things. Used together for full observability.

--- LOGGING SERVICE ---
  Captures log data from OCI resources and applications
  Log types:
    Audit Logs:    Every API call to OCI recorded; kept 90 days; cannot disable
    Service Logs:  Logs from OCI services (LB access logs, Object Storage logs, Flow Logs)
    Custom Logs:   Application logs pushed from compute instances via agent

  AUDIT LOG RETENTION: 90 days (always enabled, cannot turn off)

  OCI LOGGING ANALYTICS: Advanced log analytics and visualisation service (separate from Logging)
